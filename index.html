How I Approach an Application Issue

When I encounter an application issue, I follow a consistent sequence before escalating. This is my learning framework — not a claim of production incident ownership.

Why this order matters

Skipping reproduction or documentation forces the next person to restart discovery. In support and validation work, reproducible evidence is the product.

1. Reproduce

Can I trigger the issue again with the same steps? If not, I note what differs between attempts — device, account, timing, data state.

2. Observe

What exactly happens? Error message, blank screen, wrong data, partial success? I capture screenshots, timestamps or logs when available.

3. Isolate

Is it user-specific, environment-specific, or data-specific? I test another account, browser, network or device when possible.

4. Document

I write environment, steps, expected vs actual and evidence so another person can continue without asking me again.

5. Validate

After a fix, I return to the original steps and confirm the original expectation is met — not a nearby workaround.

Common mistakes

  • Escalating with only "it doesn't work"
  • Assuming fix worked without re-testing original steps
  • Mixing expected and actual in one vague sentence
My take: Escalation without reproduction wastes engineering time.

Sources: Personal practice framework; aligned with general ITSM troubleshooting principles.

Expected vs Actual: Writing a Useful Bug Report

The most useful bug reports answer two questions clearly: what should have happened, and what actually happened?

Template

  • Summary: One line describing the defect
  • Environment: OS, browser, app version, user role, branch/org if relevant
  • Steps: Numbered reproduction steps
  • Expected: Intended behavior
  • Actual: Observed behavior
  • Evidence: Screenshot, log snippet, request ID, HAR export
  • Impact: Who is blocked and how severely

Practical example pattern

Weak: "Payment broken." Better: "After successful card payment, learner role expected course access within 30 seconds; actual state shows locked course for 10+ minutes."

What I would document before escalating

Scope (one user vs all), first seen time, recent changes, and whether workaround exists.

How I Would Structure a Support Escalation

A good escalation preserves context so engineering does not restart discovery.

Escalation packet

  • Issue summary and customer/business impact
  • Reproduction steps verified by support
  • Environment and scope (one user vs all users)
  • Timeline: when started, frequency
  • What was already tried and results
  • Logs, correlation IDs, screenshots attached
  • Original expected behavior reference
  • Severity/priority recommendation with rationale

Common mistakes

Escalating without confirmed reproduction, or without separating workaround from verified root cause.

Priority vs Severity: Related but Not the Same

Severity describes how bad the issue is technically or for user experience. Priority describes how soon it should be addressed given business context.

A low-severity cosmetic issue on a CEO demo may have high priority. A severe bug affecting one internal test account may have low priority.

What I document

Both dimensions separately — not collapsed into one label.

Incident vs Problem vs Change: A Beginner Mental Model

Incident: Unplanned interruption or quality degradation — restore service.

Problem: Underlying cause of incidents — reduce recurrence.

Change: Planned modification that may affect services.

Fixing an incident restores service; solving a problem reduces repeat incidents. I treat these as learning concepts — not production ITSM employment claims.

Root Cause Analysis: Why Restarted the App Is Not a Root Cause

Restarting may restore service temporarily but rarely explains why failure occurred.

Useful RCA questions

  • What changed recently?
  • What dependency failed?
  • What resource was exhausted?
  • What configuration drift occurred?

Document workarounds separately from verified root cause.

A Practical UAT Checklist for a Multi-Role SaaS Product

Multi-role products need validation per role, not only happy-path admin testing.

  • Authentication and session behavior per role
  • Permission boundaries — can role A access role B data?
  • Onboarding flows for each persona
  • State transitions (pending → active → suspended)
  • Payment/entitlement alignment
  • Admin overrides and audit visibility
  • Error messages and empty states
  • Branch/org scoping where applicable

From Skillverse/Catalyx-style work: RBAC mistakes often appear only when negative tests are run.

How Role-Based Access Changes Testing Strategy

Build a matrix of roles × actions × resources. For each cell: allowed or denied? Test both.

Branch-level restrictions add another dimension — same role, different branch, different data scope.

Authentication, Authorization and Permissions

Authentication: Verifying identity (login, MFA).

Authorization: What an authenticated user may do.

Permissions: Specific grants tied to roles or policies.

Support clusters: session expiry, wrong role assignment, missing grants, branch scoping errors.

How I Use AI Agents Without Pretending AI Output Is My Manual Coding

My workflow with Cursor, Codex, Antigravity and Ollama during project-based product work:

  1. Define requirement — what should the system do?
  2. Constrain context — scope, constraints, acceptance criteria
  3. Generate — AI produces implementation
  4. Inspect — read output; do not blindly accept
  5. Test — run workflows manually
  6. Identify failures — expected vs actual
  7. Iterate — refine prompts and corrections
  8. Validate — confirm fix meets original expectation
  9. Document — record behavior and decisions
Human accountability: Requirements, judgment, testing and correctness remain human responsibilities. AI accelerates execution — it does not replace validation.

What this demonstrates

Ability to work in human-in-the-loop AI-assisted delivery — not claiming manual authorship of all generated code.

My Windows Troubleshooting Checklist

Before assuming hardware failure:

  1. Recent software or update changes?
  2. Reproducible after restart?
  3. Event Viewer errors around failure time
  4. Disk space and memory pressure
  5. Network connectivity if cloud-dependent
  6. User profile vs system-wide issue
  7. Safe Mode behavior
  8. Driver or peripheral changes
