Project-based Product Case Study

Skillverse.in

From EdTech requirements to testable learner journeys.

Requirement
User journey
AI-assisted iteration
Validation

My contribution

Requirements decomposition, user-flow definition, AI-assisted implementation review, functional validation and OpenProject tracking.

Evidence scope

Project contribution and approach. No user, revenue, conversion or retention outcomes are claimed.

01 / Problem & context

Skillverse is a multi-role EdTech project covering onboarding, authentication, courses, library, payments, entitlements and administration. The product challenge was to make expected behavior consistent across a journey rather than review each screen in isolation.

Users & workflow

Learner and administrator workflows connect registration, access and course availability. Role and account state influence what a person should be able to see or do.

Requirements

Clarify the role, preconditions, intended action and resulting access state. Connect onboarding, authentication and entitlement expectations before checking the interface.

02 / Analysis & key decisions

The existing work emphasized explicit user journeys before AI-assisted execution. Smaller, testable behavior descriptions made it possible to review output against requirements. The trade-off: rapid draft generation still required deliberate validation and correction.

  1. Problem
  2. Analysis
  3. Decision
  4. Execution
  5. Validation
  6. Learning

03 / Execution & work breakdown

Work was broken into expected journeys, implementation behavior, review findings and fix-verification tasks. OpenProject provided work-item status and delivery visibility.

Tools used in project work: OpenProject for work items; AI-assisted tools for implementation drafts and review. Generated output was reviewed against expected behavior.

04 / Validation & testing

Review expected versus actual behavior, record role and state, reproduce the issue, then re-test after correction. An illustrative acceptance check would ask whether a learner’s course access matches the confirmed entitlement state; it is a test-design example, not a claimed production incident.

Ambiguity encountered

An apparently complete screen does not establish correct behavior across account, payment and access states. Gaps in the requirement can become plausible but incorrect AI-generated behavior.

What changed after review

Expected-versus-actual findings informed requirement clarification and further implementation review. The work used correction and re-test cycles.

05 / What I learned

Acceptance criteria need to describe state changes and access rules clearly enough for someone else to repeat the check. AI-assisted output increases the importance of that clarity.

What I would improve next

Create a role/state test matrix earlier, add API-level checks as my technical depth develops, and keep clearer links between work items, acceptance criteria and review evidence.

For a Product hiring manager

What this demonstrates

Product thinking through requirement decomposition, user-flow reasoning, explicit expected behavior, delivery follow-up and validation. This is project-based practice, separate from enterprise Product Management support.

01 / Problem & context

Catalyx is an admissions and revenue-operations product concept covering leads, counselor work, follow-ups, branch operations and reporting. The challenge was to express who can act on which information, in which state.

Users & workflow

Counselor, branch and administrative concepts shaped lead assignment, follow-up scheduling and information visibility.

Requirements

Describe lead states, assignments, follow-up timing, branch restrictions and permissions. Reporting and conversion tracking were part of the requirements.

02 / Analysis & key decisions

The core decision framework connected module, role, permission and workflow state. Validating only whether someone could log in would miss the more important question: could the appropriate role see or change the appropriate lead?

  1. Problem
  2. Analysis
  3. Decision
  4. Execution
  5. Validation
  6. Learning

03 / Execution & work breakdown

Work items organized module workflows, user journeys, expected behavior, dependencies and status. OpenProject supported reviewable checkpoints during AI-assisted delivery.

Tools used in project work: OpenProject for work items; AI-assisted tools for implementation drafts and review. Generated output was reviewed against expected behavior.

04 / Validation & testing

Compare expected and actual lead transitions, assignment behavior and branch visibility. An illustrative check would cover an assigned lead within the permitted branch and a restricted record outside it. This describes test coverage, not a reported security incident.

Ambiguity encountered

Access depends on both role and context. Branch restrictions, lead state and counselor assignment needed to be considered together rather than treated as unrelated screen settings.

What changed after review

Expected-versus-actual findings informed requirement clarification and further implementation review. The work used correction and re-test cycles.

05 / What I learned

Business workflow understanding makes requirements more precise. A permission matrix and a lead lifecycle describe different parts of the same user experience.

What I would improve next

Document a compact role/branch matrix, make state-transition acceptance checks explicit earlier, and add dated feedback records so future iterations can show exactly what changed.

For a Product hiring manager

Operational problem framing, role-aware user flows, requirements clarity and delivery validation. It shows how I connect business context to testable behavior.

Product Notes

Three working frameworks

Short explanations of how I approach requirements and review.

Requirements → work items

Start with the stakeholder problem, the affected role and the intended result. Separate an agreed requirement from an assumption or an open question. Break the workflow into reviewable work items, each with preconditions, expected behavior and acceptance criteria.

Keep a link between the original context and the work item. When feedback changes the expectation, update the requirement and the acceptance check together. Clarification supports a decision; priority and scope still need an accountable decision-maker.

Acceptance criteria & UAT

A useful acceptance criterion describes observable behavior: given a role and starting state, when an action occurs, what should happen? Include relevant permissions, invalid inputs and state changes alongside the happy path.

For UAT, record the starting conditions, steps, expected result and actual result. Make the finding repeatable, clarify any disputed expectation and re-test the agreed correction. A successful screen is only part of a successful workflow.

AI-assisted delivery needs human review

Use a clear requirement to constrain an AI-assisted draft. Review the output against user flows, roles and states; a plausible interface does not establish correct behavior.

Separate generation from acceptance. Record gaps, make the correction explicit and repeat the check. Keep responsibility for requirements, review and acceptance visible rather than treating generated output as evidence of correctness.
