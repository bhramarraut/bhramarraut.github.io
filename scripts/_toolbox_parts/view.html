01 / Method

How I choose tools

Six principles that keep tool decisions tied to delivery reality rather than novelty.

  1. Start with the problem

    Name the workflow failure first. Tool shopping before problem framing usually produces shelfware.

  2. Prefer the simplest adequate option

    Adequate for the job beats elegant for the brochure. Complexity has to earn its keep.

  3. Judge total cost of ownership, not license price

    Training, integration, maintenance, support and exit cost matter as much as the sticker.

  4. Avoid unnecessary lock-in

    Prefer portable formats and clear export paths when the work product needs to outlive the tool.

  5. Match the team’s operating reality

    Evaluate when adoption friction, access control and support load fit the people who will run it.

  6. Automate after the workflow is understood

    Stabilize the manual path first. Automation without a clear process amplifies confusion.

02 / Implementation

Implementation playbooks

Four working patterns — what problem they address, how the stack fits together, and where the trade-offs sit.

Playbook 01 Used in project work

AI-Assisted Product Delivery

Problem: turn ambiguous product requirements into testable workflows while using AI agents for implementation draft — without treating generated output as finished work or claiming manual full-stack authorship.

Flow

  1. Requirement
  2. Constraints
  3. AI draft
  4. Inspect
  5. Validate
  6. Document

Tool map

  • OpenProject — work items, status, dependencies
  • Cursor / Codex / Ollama — assisted implementation drafts
  • Obsidian — requirement notes and handover

Why this combination

  • Keeps human ownership on requirements, judgment and validation
  • Makes delivery status visible while AI accelerates draft output
  • Fits Skillverse and Catalyx project work patterns

Trade-offs

  • Faster drafts increase the need for expected-vs-actual checks
  • Weak requirements produce plausible-but-wrong behavior quickly
  • Evaluate when the team can inspect and test AI output deliberately

Playbook 02 Hands-on / implemented

Local-First Knowledge Publishing

Problem: keep thinking in local Markdown, then publish a browsable knowledge base without locking notes into a proprietary cloud editor.

Flow

  1. Obsidian
  2. Markdown
  3. Git
  4. Manifest
  5. Pages

Tool map

  • Obsidian — local notes and linking
  • Git — versioned source of truth
  • Build script + GitHub Pages — index and publish

Why this combination

  • Portable plain-text notes survive tool changes
  • Publishing stays reproducible from the repo
  • Works offline during drafting

Traditional wiki vs this stack

  • Traditional: faster collaborative editing, more platform coupling
  • This stack: stronger ownership and exportability, more publish discipline
  • Evaluate when the knowledge product needs local control more than live multiplayer editing

Playbook 03 Building

Application Issue Investigation

Problem: turn vague “it doesn’t work” reports into reproducible evidence that another person can act on — with SQL and API checks entering the toolkit as they mature.

Flow

  1. Reproduce
  2. Observe
  3. Isolate
  4. Document
  5. Validate

Tool map

  • Browser / app UI — reproduction path
  • SQL — building; data-side checks when needed
  • Postman — building; request/response inspection

Why this combination

  • Framework stays useful before deep tooling fluency
  • SQL and Postman extend the same evidence model
  • Documentation quality determines escalation speed

Trade-offs

  • UI-only checks miss backend state; API/data checks need access and care
  • Building depth means some paths are still deliberate practice
  • Evaluate when the environment allows safe read access to data and APIs

Playbook 04 Reference

Lean Project Delivery Stack

Problem: run small product delivery with visibility and low overhead when a full enterprise toolchain is not available or not yet justified. This is a reference pattern from project-based work — not an employment claim.

Flow

  1. Scope
  2. Track
  3. Build / assist
  4. Validate
  5. Publish evidence

Tool map

  • OpenProject — lean work tracking
  • Obsidian + Git — decisions and publishable notes
  • AI agents — draft acceleration under review

Why this combination

  • Enough structure for status without heavy process theater
  • Keeps artifacts portable across environments
  • Useful as a comparison baseline against enterprise suites

Trade-offs

  • Lean stacks shift cost into operator skill and discipline
  • Enterprise suites may win on SSO, compliance and shared support
  • Evaluate when team size, audit needs and integration depth change

03 / Compare

Compare by need

Lean and enterprise options side by side. Use “evaluate when” — not “best tool” — language for each need.

Lean

OpenProject + Markdown status

Work items, priorities and dependencies with lightweight documentation beside the tracker.

  • Evaluate when a small team needs visibility without a heavy PMO suite
  • Lower license cost; more setup and operating discipline
  • Fits project-based delivery with clear ownership
Enterprise

Jira / Azure DevOps-class suites

Broad workflow engines, permission models and ecosystem integrations common in larger orgs.

  • Evaluate when SSO, audit trails and cross-team standards dominate
  • Higher platform cost; shared support and established patterns
  • Often already decided by the organization — adopt the house standard
Lean

Obsidian → Git → Pages

Local Markdown notes published as a versioned knowledge base.

  • Evaluate when portability and offline drafting matter most
  • Publishing requires a deliberate build/publish step
  • Strong fit for personal or small-team knowledge products
Enterprise

Confluence / SharePoint-class platforms

Shared editing, search, permissions and org-wide templates in one place.

  • Evaluate when many authors and access control are the core need
  • Faster collaboration; more platform coupling
  • Export and long-term ownership need an explicit plan
Lean

Cursor / Codex + Ollama

Hosted agents for speed, local models when privacy or offline constraints apply.

  • Evaluate when draft acceleration must stay under human review
  • Local models trade peak capability for control
  • Validation and acceptance criteria remain non-optional
Enterprise

Org-governed AI platforms

Vendor suites with admin controls, data policies and approved model access.

  • Evaluate when compliance and data residency decide the shortlist
  • Procurement and policy overhead replace DIY setup
  • Use the approved channel rather than shadow tooling
Lean

LocalSend (LAN-first)

Cross-platform local network transfer without a cloud middle hop.

  • Evaluate when devices share a network and files should stay local
  • No account maze; limited to reachable peers
  • Pair with clear naming so handoffs stay traceable
Enterprise

Managed share / MDM channels

Org drives, secure file exchange and device-managed transfer policies.

  • Evaluate when auditability and retention rules are mandatory
  • Slower for ad-hoc LAN swaps; stronger governance
  • Follow the house channel when regulated data is involved

04 / Fit

When open source wins / when enterprise wins

Neither side wins by default. The decision follows constraints, not preference.

When open source wins

Evaluate OSS when control, portability and operator skill are available.

  • Portable artifacts Markdown, Git and open formats outrank proprietary containers
  • Constraint-fit tooling Offline, LAN-first or self-hosted needs dominate
  • Small team ownership One clear owner can run upgrades and backups
  • Learning surface Understanding the stack is part of the value

When enterprise wins

Evaluate enterprise when coordination and governance outweigh DIY cost.

  • Compliance & SSO Identity, audit and policy are non-negotiable
  • Shared support model Vendor or central IT carries operational load
  • Cross-team standards Many groups must share one workflow language
  • Integration depth Existing ERP/ITSM/IdP connections already decide the shortlist

05 / Cost reality

Open source ≠ zero cost

License price is one line item. Operations are the rest of the bill.

TCO still includes

  • Setup, upgrades and backups
  • Training and onboarding time
  • Integration and glue work
  • Security review and access design
  • Support load when something breaks

Lean without cheap

A lean stack can be the right fit and still demand real operator time. “Free to download” is not “free to run well.”

What I optimize for

Clear ownership, exit paths and enough structure for evidence — not the lowest sticker price in isolation.

Business model patterns (general)

  • Community + self-host — you carry operations
  • Open core — base free; paid features or hosting
  • Managed OSS — vendor runs the open stack for you
  • Enterprise license — pay for suite, support and compliance features

06 / Gate

Before I add a tool

Twelve questions that slow impulse adoption and surface switching cost early.

  1. What exact problem fails today without this tool?
  2. What does success look like in one workflow, not a feature list?
  3. What existing tool already covers 80% of the need?
  4. Who owns setup, access and day-2 operations?
  5. What data enters the tool, and where does it live?
  6. How do we export or leave if the tool stops fitting?
  7. What training time does the team actually have?
  8. Does it integrate with the current identity and tracker?
  9. What breaks if the tool is offline for a day?
  10. What evidence will prove the tool earned its keep in 30 days?
  11. What is the switching cost from the current method?
  12. Are we automating a workflow we already understand?

Switching cost is part of the decision: migration, retraining, broken links and lost muscle memory often exceed the license delta.

07 / Cases

Two illustrative mini cases

Short examples of how the principles show up in practice.

Case A · Delivery

Requirements stayed fuzzy; AI drafts looked complete

On Skillverse-style work, AI-assisted implementation moved quickly once prompts were rich — and produced the wrong behavior just as quickly when acceptance criteria were vague.

The fix was not “more tools.” It was tighter requirements, OpenProject visibility, and expected-vs-actual validation before calling a slice done.

Case B · Knowledge

Notes lived in too many places to publish

Scattered docs made reuse slow. Moving the working set into Obsidian Markdown, versioning in Git, and publishing through a manifest kept the same files as both draft and site source.

The trade-off is publish discipline: fewer magic sync buttons, clearer ownership of what is public.
